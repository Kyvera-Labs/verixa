# Token Storage

**Never store a bearer token in plaintext.** Store a hash, and compare
hashes. This applies to every secret a holder can present to prove
something: invitation tokens, password-reset tokens, email-verification
tokens, API keys, session refresh tokens.

Verixa's first application of this is the invitation token (Issue 045).

## The rule

A **bearer token** is a secret whose mere possession grants something. Anyone
holding a valid invitation token can accept that invitation, as the invited
party. Anyone holding a password-reset token can reset that password.

Because possession _is_ authorization, the token must exist in exactly one
place: with the person you gave it to. Not in your database, not in your
logs, not in a backup.

The pattern:

1. Generate a high-entropy random token.
2. Hash it. Store **only** the hash.
3. Send the raw token to the recipient, once.
4. Discard the raw token from memory.
5. On presentation, hash the incoming token and look up by that hash.

At no point after step 3 can the system produce the raw token — which is the
entire point.

## Why "it's short-lived" is not an exemption

Invitation tokens expire in seven days. That is not a mitigation. A leaked
token is exploitable immediately, and seven days is an eternity. Expiry
limits the _window_; it does nothing about the _exposure_.

The threat here is not "someone brute-forces a token." It's the mundane
reality that databases get read by more people and systems than intended: a
leaked backup, a SQL-injection read, an over-broad analytics grant, a
support engineer with production access, a misconfigured replica, a screenshot
in a bug report. Hashing means every one of those yields nothing usable.

## Why SHA-256 here, not argon2

Passwords will use argon2 (Phase 04). Invitation tokens use plain SHA-256.
That difference is deliberate, and the reasoning generalizes.

A slow, memory-hard KDF like argon2 exists to defend **low-entropy secrets
that humans chose**. Real passwords come from a small, heavily-skewed
distribution, so an attacker with the hashes can guess intelligently — and
making each guess expensive is the only defense.

An invitation token is 128 bits of `randomUUID()` entropy, from a CSPRNG. The
search space is roughly 3.4 × 10³⁸. There is no guessing strategy; brute
force is not a threat model. Deliberate slowness would buy nothing and cost
something real: token lookup happens on a user-facing request path, and
argon2 is slow by construction.

The decision rule: **argon2 for secrets humans chose, fast hashes for secrets
a CSPRNG chose.** Applying the password answer to a random token is a common
and expensive cargo-cult.

One property SHA-256 does need to keep: it must be a _lookup key_. Because
the hash is deterministic, `findByToken` is a single indexed query on
`token_hash`. A salted hash would make lookup impossible without scanning
every row — which is fine for passwords (you already know which user's hash
to compare) and unworkable here.

## Timing-safe comparison

`Invitation.matchesToken()` compares with `crypto.timingSafeEqual`, not `===`.

String equality short-circuits at the first differing byte, so the time it
takes leaks how much of the guess was right. Across enough attempts, that
recovers a secret byte by byte.

For this specific case that attack is impractical — the comparison sits
behind a database round-trip whose variance dwarfs the signal, and the token
has 128 bits of entropy anyway. It's done regardless because it costs
nothing, and because "compare secrets in constant time" should be reflexive
rather than a judgment call made correctly each time. Phase 11 treats this
properly.

## What this looks like in the schema

```prisma
model Invitation {
  tokenHash String @unique @map("token_hash")
  // ...
}
```

There is no `token` column, and no way to add one by accident: the domain
entity has no raw-token field either. `Invitation.create()` returns the raw
token _alongside_ the entity rather than on it, so the only code that ever
sees it is the code that just issued it.

```ts
const { invitation, token } = Invitation.create({ ... });
await repository.save(invitation);  // stores the hash
await mailer.send(email, token);    // Phase 14 — the one place the raw token goes
```

Because the raw token only exists in that return value, forgetting to hash it
before storage isn't a mistake you can make — there is nothing unhashed to
store.

## Checklist for future tokens

Every new bearer token in Verixa should satisfy all of these:

- [ ] Generated by a CSPRNG (`randomUUID`, `randomBytes`) — never `Math.random`
- [ ] At least 128 bits of entropy
- [ ] Only the hash is persisted; no column, log, or metric holds the raw value
- [ ] The raw value is returned exactly once, at creation
- [ ] Lookup hashes the incoming value; callers never construct a hash
- [ ] Comparison is timing-safe
- [ ] Has an expiry, and expiry is enforced on read rather than assumed
- [ ] Single-use where applicable, enforced by a status transition
